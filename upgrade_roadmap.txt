PART 1 — WHAT IS BUILT (shipped today)
================================================================================

Architecture
  - Three-service split: React (Vite) frontend, thin Express API layer,
    stateless FastAPI orchestrator. Clean separation — routing/DB in Node,
    the whole AI pipeline in Python.
  - Deployed end-to-end on Render free tier + MongoDB Atlas M0. It runs.

AI pipeline (the real work — FastAPI)
  - 7-stage RAG pipeline: query expansion -> parallel retrieval ->
    normalization/dedupe -> hybrid re-ranking -> context build ->
    grounded LLM reasoning -> response assembly.
  - Three LIVE medical sources fetched in parallel (httpx.gather):
    PubMed (E-utilities), OpenAlex, ClinicalTrials.gov v2. ~210 raw ->
    ~170 after cross-source dedupe by DOI/PMID/NCT-ID.
  - Domain-specialized ranking funnel: BM25 pre-filter -> PubMedBERT
    (S-PubMedBert-MS-MARCO) dense cosine -> Reciprocal Rank Fusion ->
    recency + multi-source credibility boosts -> MedCPT cross-encoder ->
    source-balanced MMR -> top 10. This is well beyond a naive vector search.
  - Cite-or-abstain grounding: every claim carries title/authors/year/URL +
    supporting snippet; the system abstains instead of hallucinating.
  - Clinical-trial geo-filtering via Nominatim geocode + ClinicalTrials geo API.

Real-time UX
  - True SSE streaming end-to-end: FastAPI -> Express (proxied/parsed) ->
    React. Live pipeline stage progress + token-by-token LLM output.
  - Edge-proxy buffer-busting padding so streaming survives Render/Cloudflare.
  - Honest cold-start notice: if a spun-down free-tier service hasn't responded
    within 5s, the UI explains it's waking up rather than showing a dead spinner.
  - Client checks HTTP status before parsing SSE (was BUG-2): a 401 shows
    "session expired, log in again", a 404/5xx a clear retry message, instead of
    feeding an error page into the stream parser and looking like no response.
  - Stop button (was UX-4): an AbortController cancels an in-flight request
    mid-pipeline and shows "Generation stopped" cleanly instead of hanging.

App layer
  - JWT auth (signup/login/me), bcrypt-hashed passwords.
  - Expired-session handling (was UX-5): a 401 routes the user back to the login
    screen showing "session expired, log in again" instead of a silent dead
    request. (A refresh-token flow to avoid the interruption entirely remains a
    possible future nicety, not required for small users.)
  - Session model with static intake context (disease/intent/location/name);
    ChatGPT-style session sidebar; multi-turn history merged into each query.
  - Resumable sessions (was UX-2): clicking any past session reopens it with a
    live input that appends new turns to that session's history.
  - Copy / export answers (was UX-6): every structured answer has Copy (to
    clipboard as Markdown) and Download (.md) actions for saving and sharing.
    PDF is intentionally skipped — browser print-to-PDF covers it for free.
  - "Not medical advice" disclaimer shown at signup, at consultation start, and
    on every answer.
  - Landing page (LandingPage.jsx + landing.css): a Linear-styled marketing page
    with an animated chat demo, scroll reveals, feature/step sections, and a
    clinical-teal accent — shown before auth; "Get started"/"Sign in" gate into
    the app (App.jsx showAuth). Design chosen from awesome-design-md per its
    rules.txt default (Linear), built the flipkart way; icons are inline SVG (no
    lucide dependency). The old my-architecture.png was dropped and the README
    architecture rewritten as a 5-layer mermaid diagram.
  - Request IDs + structured JSON access/error logs + a central Express error
    handler (was REL-1): errors return a generic message + request id, never a
    stack trace (also helps SEC-7); Express 5 async errors route here too.
  - Ownership-scoped chat routes (was SEC-1): /chat and /chat/stream load the
    session with { _id, userId }, so no one can read or post to another user's
    session (matches the session routes, which already scoped correctly).
  - No JWT secret fallback (was SEC-2): the server fails to boot if JWT_SECRET is
    unset, and the secret is read at call time — no hardcoded default anywhere.
  - Env-driven CORS allow-list (ALLOWED_ORIGINS): the Express origin allow-list
    moved from hardcoded to .env (comma-separated), defaulting to the deployed
    frontend + localhost.
  - Rate limiting (was SEC-4): strict per-IP limit on /api/auth (brute-force /
    signup spam) and a per-user quota on /chat (cost/DoS), behind trust-proxy so
    limits key on the real client IP.
  - No debug/inspect endpoints (was SEC-5): deleted /api/db-inspect (listed all
    databases + collections) and /api/db-ping (unauthenticated Mongo write);
    health checks stay static (matches flipkart's pattern of not exposing them).
  - Input-size caps (was SEC-6): message capped at 4000 chars at the Express
    boundary, a 16kb JSON body limit, and a matching cap in the FastAPI request
    validator — no one can inflate LLM cost/latency without a ceiling.
  - No error-detail leakage (was SEC-7): chat + ping endpoints log the real
    error server-side with the request id and return only a generic message +
    that id — never raw err.message or pipeline stderr.
  - Password minimum raised to 8 (frontend + route + schema).
  - HF throttling (SCALE-2, HF-only by choice — no self-host): LLM calls to the
    HF Inference API are bounded by a concurrency semaphore (LLM_CONCURRENCY,
    default 3) and retried with backoff on 429s; the embedder already backs off.
  - Redis caching (SCALE-5, active): query-result cache (cache.js) + embedding
    cache (redis_cache.py) on Upstash — configured and verified from Node +
    Python; falls back to Mongo / no-cache if REDIS_URL is unset.
  - Semantic query cache (SCALE-1): a first-turn question is embedded and
    cosine-matched (>=0.97) against recent questions in the same disease|intent
    bucket in Redis; a near-duplicate returns the cached answer and SKIPS the
    entire pipeline (retrieval + ranking + LLM). High threshold + first-turn-only
    so a rephrase hits but a different question never does. (The full PubMed
    corpus pre-index remains true-10k-scale infra, not needed for the demo.)
  - Per-user quota (SCALE-3): 3 credits, 1 credit = 1 question, atomic
    check-and-decrement (User.credits), 402 "out of questions" when exhausted;
    per-IP/per-user rate limits (auth, chat, session 30/hr) already in place.
    (Rate-limit maxes + default credits are env-tunable — AUTH/CHAT/SESSION_RATE_MAX,
    DEFAULT_CREDITS — so a load test can lift its own guards.)
  - Frontend served as a Render static site (CDN-delivered via Cloudflare edge) —
    static assets are never a bottleneck. (Was SCALE-7.)
  - Load-test harness (backend-node/load_test.py, modeled on multi-crew-lead-
    coordinator's): spawns the REAL Express with the FastAPI pipeline stubbed
    (an SSE stub that sleeps --lead-seconds → zero HF cost), then either ramps
    read concurrency to find the healthy ceiling or compares idle-vs-saturated
    latency (reads vs reads-while-N-chat-streams-in-flight, exposing Mongo-pool
    contention); --base-url ramps a live deployment read-only. Reports to
    load_test_results/. Running it already caught + fixed an IPv6-unsafe
    rate-limit keyGenerator (now uses ipKeyGenerator).
  - Observability (SCALE-6), wired the flipkart way (observability.py, OTLP):
    LLM generation spans -> Langfuse AND Grafana, HTTP endpoint spans (FastAPI
    instrumentor) -> Grafana, and a chat_messages_total counter -> Grafana. All
    no-op unless LANGFUSE_* / GRAFANA_OTLP_* are set; nothing raises. Verified
    init + span creation. Deferred (optional, as flipkart also skips): Sentry
    error-grouping and a token/cost dashboard.
  - CI/CD + Docker (ported from flipkart): .github/workflows/ci.yml runs four
    gates — backend-node (npm ci + node --check), backend-python (ruff +
    compileall + load_test --selftest), frontend (npm ci + lint + build), and a
    docker job building all three images (no push, gha cache). A deploy job gated
    on main + RENDER_DEPLOY_HOOK_* secrets pokes Render, skipping gracefully if
    unset. Dockerfiles for all three services (non-root, healthchecks) +
    docker-compose.yml + frontend/nginx.conf + .dockerignore + ruff.toml. All
    gates verified locally except the Docker build (no daemon — the CI docker job
    is the first real build). Fixed a real rules-of-hooks bug it surfaced
    (conditional useState in StructuredResponse).
  - Mongo query-result cache keyed on SHA-256(disease|intent|message + prior
    chat history), 24h TTL, skips the entire pipeline on exact repeats. History
    is in the key (was BUG-1) so identical follow-up text in different chats
    can't return the wrong conversation's cached answer; first turns still
    share a key, preserving cross-session hits. Keys are also normalized for
    case/punctuation/possessive/whitespace (was UX-3) so trivial re-typings
    ("Parkinson's?" vs "parkinsons") still hit. (Synonym/abbreviation matching
    — DBS vs deep brain stimulation — is left to the semantic cache in SCALE-1.)
  - Sensible DB indexing already in place: Session.userId index,
    Message compound index {sessionId, createdAt}, Cache unique key +
    TTL index on expiresAt. (Good — this is often missed.)

Bottom line: the hard, differentiating part (retrieval + ranking + grounded
reasoning over live medical literature) is genuinely done and is the strong
part of the project.

PART 3 — PRODUCTION READINESS (can small/real users use it now, safely?)
================================================================================

Verdict: OK for a small, trusted user base. The go-live blockers are fixed and
the security hardening is done (all in PART 1): ownership scoping on session +
chat routes, no JWT-secret default (fail-fast), auth + per-user rate limits, no
debug/inspect endpoints, input-size caps, and no error-detail leakage.

Deploy-time must-do (not code): set a strong JWT_SECRET in the Express env (it
refuses to boot without one); set ALLOWED_ORIGINS if the frontend origin differs
from the default.

The only deliberately out-of-scope item is email verification / password reset
(needs SMTP) — fine to skip for a small, trusted base, revisit before public
signup. Everything else that makes it safe at small scale is in PART 1.

PART 4 — SCALING TO 10k+ USERS
================================================================================

The architecture (stateless FastAPI, thin Express, external LLM) is
scale-friendly in shape. What breaks at 10k users is the reliance on
best-effort free/shared external services on the hot path.

(SCALE-1 semantic cache, SCALE-2 HF throttle, SCALE-3 quota+rate-limits, and
SCALE-5 Redis cache are DONE — see PART 1. What remains below is infra for real
10k-user scale.)

[SCALE-4] Infrastructure: leave the free tier.
  - Express + FastAPI: paid, always-on, horizontally scaled behind a load
    balancer (autoscale on CPU/queue depth). FastAPI is already stateless — good;
    add a concurrency limit + worker pool so one instance can't be overwhelmed.
  - SSE at scale: cap concurrent streams per instance; ensure LB doesn't buffer;
    sticky routing not required (stateless) but connection limits matter.
  - MongoDB: M0 -> M10+ with proper sizing. Indexes are already good; add one
    for Message ownership lookups once SEC-1 scopes chat by user. For read-heavy
    load (history + ownership lookups on every chat), add a read replica and
    route those reads to a secondary (Atlas replica set / read preference), and
    tune the Mongoose connection pool (maxPoolSize) per instance.

[SCALE-8] Shared rate-limit store once you run more than one instance.
  Depends on adding rate limiting first (SEC-4, Part 3). express-rate-limit's
  default store is in-memory per-process, so with two or more Express instances
  the per-IP / per-user limits stop being coordinated and a user effectively
  gets N times the intended limit.
  Fix: back the limiter with Redis (rate-limit-redis / Upstash).
  Note: this is the ONLY piece of per-instance state in the way of horizontal
  scaling. FastAPI is already stateless, the JWT is stateless, and the
  query-result + embedding caches are shared (Mongo, or Redis when configured),
  not per-process — so once the rate-limit counters move to Redis, any
  instance can serve any request behind the load balancer with no sticky
  routing.

[SCALE-9] Secrets manager instead of per-service .env files.
  At real/multi-instance deployment, move HF_TOKEN, JWT_SECRET, MONGO_URI, the
  NCBI key, etc. out of .env into a managed store (Doppler / AWS Secrets Manager
  / Render env groups) with rotation. Directly reinforces SEC-2 — a leaked or
  defaulted signing secret is full account takeover.

Recommended order for what's left:
  1. SCALE-4 infra (always-on + autoscale + Atlas tier + read replica).
  2. SCALE-8 rate-limit store in Redis (the moment there's a second instance).
  3. SCALE-9 secrets manager.
  (The biggest remaining lever at true 10k scale is a pre-indexed PubMed vector
  store so uncached queries don't hit the live APIs — deliberately deferred; the
  semantic cache already covers the demo's hot path.)
